# Learning-record guidance

Use this to interpret and update the notebook; the template supplies its initial
shape. Preserve existing history and useful formatting rather than forcing a
migration on every review.

## Concepts and evidence

Within the resolved notebook, keep one record per independently assessable
concept, with a stable ID. Link each
index entry to its concept heading or file. Search
the index by meaning before creating one: different wording or a new project
does not make a new concept. Use topics to aid lookup. Merge examples that teach
the same mechanism; keep version-specific behavior explicit and link related
concepts when their contracts differ.

A lesson explains the code evidence, assessment, mechanism and limits, suggested
application, and supporting sources. Attach project, date, file and symbol to
observations. Favor small portable examples over copying whole project files.
Correct inaccurate or outdated lessons and answer keys explicitly.

For example, another closure in project B can extend the existing JavaScript
closure record from project A. It adds an encounter, not a new lesson or an
automatic claim of understanding. A framework's stale-state behavior may need
a linked lesson because framework lifecycle rules add a different condition.

## Progress

Use these understanding states:

| State | Evidence |
| --- | --- |
| Unassessed | Explained or observed, without a learner attempt. |
| Needs reinforcement | Recall only, an incorrect or partial answer, or help was needed. |
| Demonstrated | Independently applied to a changed example and explained why. |

Reading, agreement, and accepting AI-generated code are exposure. Record
self-reported confidence separately. A later failed attempt can return a concept
to needs reinforcement while preserving earlier evidence. Technical uncertainty
belongs in open questions, not in the learner's assessment.
Describe unassessed code as consistent with a principle; credit successful
learner transfer only when the learner applies and explains it independently.

`Encounters` counts distinct coding sessions where the concept was evidenced,
once per concept per session across projects using this notebook. Start at 1 for
a newly reviewed concept, or 0 for a concept introduced only for practice; omit
code evidence when none exists. Reprocessing the same session,
practicing a question, or editing the notebook adds no encounter. Keep enough
session/date and project context in history to recognize repeats. Preserve
unknown historical counts as unknown.

Record actual learner responses, outcomes, and hints used; unanswered prompts
remain pending. Update `Last practiced` only after an attempt. Keep index values
consistent with their concept records.

## Practice and spacing

Give each new verified concept its own focused question and collapsed answer
with reasoning, preferably using changed conditions. Save these for later study;
ask only one question at a time in conversation. Give beginners a
worked example before independent practice; answer-visible attempts are assisted.
Exclude unresolved or superseded claims from recall practice.

Respect existing review preferences and intervals. Otherwise suggest tomorrow
for a new concept or a gap, and a longer interval after successful recall on a
later day. Same-day retries do not extend the interval; unanswered prompts keep
their date. These are practice suggestions, not an adaptive Anki scheduler.

Demonstrated concepts stay available for spaced practice without receiving the
same full explanation in each code review. Revisit them when requested, when a
new condition matters, or when learner evidence exposes a gap. A due date alone
does not interrupt an unrelated coding task or create an automatic reminder.
